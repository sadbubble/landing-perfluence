# Передача проекта

Документ для того, кто продолжит работу в новой сессии или на другой
машине. Здесь то, чего не видно из кода: почему сделано именно так, где
закопаны грабли и что спрашивать у заказчика.

**Обновлено:** 31 августа 2026 (дополнено после разбора формы Qbox)

---

## С чего начать

```bash
npm install
```

```bash
npm run dev
```

- `/` — лендинг
- `/d/AG-K7F21` — он же по персональной ссылке дилера, код подхватывается
- `/privacy` — политика обработки персданных
- `/?themes=1` — панель выбора оформления (осталась с этапа согласования)

Переменные окружения **не нужны**: лендинг работает без них.

---

## Первое, что нужно знать

**Системы контроля версий в проекте нет.** Ни git, ни резервных копий.
Любое удаление необратимо. Прежде чем что-то менять всерьёз — заведите
репозиторий:

```bash
git init && git add -A && git commit -m "Исходное состояние"
```

Это стоит сделать до первой правки. Проект пережил уже несколько крупных
переделок дизайна, и каждый раз откат был невозможен.

## Устройство

React 19 + TypeScript + Vite 8. Одна страница, роутинг на `react-router`.

```
src/
  pages/Landing.tsx     вся страница: состояние, обработчики, разметка секций
  pages/Privacy.tsx     текстовая страница политики
  components/           секции и элементы
  content/ru.ts, kk.ts  ВСЕ тексты; одинаковый набор ключей в обоих файлах
  content/privacy.ts    текст политики отдельно
  lib/dealer.ts         чтение кода дилера из адреса
  lib/api.ts            отправка заявки — ТОЧКА ПОДКЛЮЧЕНИЯ QBOX
  lib/phone.ts          нормализация номеров, покрыта тестами
  index.css             все стили и токены оформления
public/                 картинки и шрифты
_archive/               убранное из проекта, см. ниже
assets-src/fonts/       исходные .otf Helvetica Neue (6 МБ, в сборку не идут)
```

**Тексты только в `content/*.ts`.** В разметке не должно быть ни одной
русской строки: иначе казахская версия рассыплется. Оба файла обязаны
иметь одинаковые ключи.

**Цвета только через токены в `:root`.** Палитра из гайда заказчика.

## Решения, которые легко случайно сломать

### Палитра: два синих, не один

Гайд даёт `#008EFF` как основной. Но **белый текст на нём даёт контраст
3.33 при норме 4.5** — на нём нельзя писать белым. Поэтому:

- `--brand` `#008EFF` — акценты, обводки, подложки, крупная графика;
- `--brand-strong` `#0044BC` — заливка под белым текстом: все кнопки;
- `--brand-light` `#00D9FF` — градиенты и декор.

Оба цвета из гайда. Если увидите «странно, почему кнопки тёмно-синие» —
вот почему. Не меняйте на `#008EFF`, не пересчитав контраст.

### Разноцветные шапки тарифов — отменены дважды

Сначала были разноцветные (оранжевый Bereket и т.п.), потом синие по
гайду, потом заказчик вернул разноцветные, потом попросил переделать всю
секцию по своему макету — и сейчас карточки **белые, без цветных шапок**.
Файл `_archive/unused-ui/tariffAccents.ts` — от той версии.

### Шрифт подключается файлами

Helvetica Neue есть только в системах Apple. В `public/fonts/` лежат
четыре начертания в woff2, урезанные до нужных символов: 156 КБ вместо
6,4 МБ исходников. **Казахские буквы `әғқңөұүһі` в них проверены** — это
была главная неизвестность.

Внешних шрифтовых сервисов на странице нет намеренно: страница поедет на
сервер КТ, лишняя зависимость от чужого домена там ни к чему.

### Картинки баннеров подобраны расчётом, а не на глаз

У верхнего и нижнего баннера поверх картинки лежит полупрозрачная вуаль.
Её плотность подбиралась **измерением контраста по реальным пикселям
файла**, а не подгонкой на глаз. Дважды выяснялось, что «выглядит
нормально» означает 2.4–3.9 при норме 4.5.

У нижнего баннера вдобавок кадр прижат к низу (`background-position:
center bottom`): при центрировании яркое свечение из верхней части
картинки ложилось ровно на строку заголовка.

**Если меняете размеры баннеров или текст в них — пересчитайте контраст.**
Геометрия обрезки меняется, и прежний расчёт становится недействителен.

### Мобильные баннеры без картинок

На телефоне широкие кадры обрезаются до полосы, где не остаётся ничего
полезного. Обе картинки на мобильном отключены — там рисуется градиент.
Это и резче, и легче.

### Высота баннера считается от окна, а не от ширины

Верхний баннер занимает ровно высоту окна. Кегль заголовка ограничен
и по высоте: `min(clamp(...), 8.5svh)`. Без этого на широком, но невысоком
окне (Windows со 125% масштабом даёт около 1360×625) низ баннера уезжал
за экран.

### Обязательность полей

Обязательны: телефон, ФИО, тариф, согласие. **Адрес необязателен** — это
решение заказчика, он уточняется при обзвоне. Комментарий тоже.

Раньше обязательными были все поля, кроме комментария. Если увидите в
переписке или старых заметках обратное — актуально это.

### Ловушка для ботов

В форме есть скрытое поле `company`. Оно за экраном через `position/left`,
а не через `display:none` — иначе боты его игнорируют. Из-за этого оно
проходит проверки на видимость, и в модальном окне пришлось отдельно
отсекать его из таб-порядка по `tabIndex < 0`.

## Что лежит в `_archive/`

Ничего оттуда не используется. Перенесено, а не удалено, потому что нет
git — если понадобится, доставать оттуда.

| Папка | Что там | Почему убрано |
|---|---|---|
| `backend/` | Схема БД, RLS, Edge Function приёма заявок, админка с отчётами и выгрузкой в Excel | Заказчик отменил бэкенд: заявки идут в Qbox |
| `figma/` | Исходный экспорт из Figma Make | Код с тех пор переписан полностью |
| `unused-ui/` | Секция «Преимущества», логотип, цвета шапок тарифов | Убраны по просьбе заказчика |

В `backend/` лежит рабочая реализация: миграции, политики доступа, приём
заявок с валидацией, антиспамом и дедупликацией, панель менеджера с
фильтрами и выгрузкой по дилерам. Если Qbox не подойдёт — это готовая
замена, а не черновик.

## Следующий шаг: Qbox

Заявки должны уходить во внутреннюю платформу Qbox. Не сделано, потому что
неизвестны условия подключения.

### Самое важное: коду дилера в Qbox некуда лечь

Заказчик показал форму Qbox. В ней три поля: **Имя, Номер телефона,
Город** — и всё. Места под код дилера нет.

Это ломает главное требование ТЗ (п.5): по каждой заявке должно быть
видно, кто из дилеров привёл клиента, и на этом строится месячный расчёт
с сотрудниками. Без решения лендинг будет собирать обезличенные заявки.

Варианты, по убыванию удобства:

1. **Скрытое поле в Qbox**, заполняемое из параметра ссылки. Идеально.
2. **UTM-метки**, если Qbox их принимает и показывает в выгрузке. Код
   можно слать как `utm_content`.
3. **Отдельная форма на каждого дилера.** Работает, но при двадцати
   дилерах это двадцать форм и ручная операция на каждого нового.

Согласия на обработку персданных в той форме тоже нет — его нужно
добавить, это требование закона РК, а не вопрос конверсии.

**Что ещё выяснить у владельцев Qbox:**

1. Есть ли HTTP API для приёма лидов и какой у него формат?
2. Какая авторизация — ключ, токен, подпись?
3. Разрешает ли Qbox запросы **из браузера** (заголовки CORS)?

Третий вопрос важнее всех. Лендинг — статика без бэкенда, значит запрос
пойдёт прямо из браузера клиента. Если Qbox этого не разрешает, заявку
отправить не выйдет вообще. И даже если разрешает — **ключ доступа
окажется в коде страницы**, видимый любому, кто откроет исходники.

Обычное решение — крошечный обработчик на том же сервере КТ: страница
шлёт заявку ему, он подставляет ключ и передаёт дальше. Это несколько
десятков строк, но **это надо заложить в запрос к КТ заранее**, пока
сервер только выделяют, иначе придётся просить второй раз.

**Точка подключения одна:** функция `handleSubmit` в
`src/pages/Landing.tsx` и `submitLead` в `src/lib/api.ts`. Больше нигде
менять не придётся.

Что уже собирается и должно дойти до Qbox: телефон, ФИО, адрес, тариф,
комментарий, согласие с версией текста, **код дилера**, метки UTM и язык
страницы.

## Открытые вопросы к заказчику

- **Тексты.** Заказчик говорил, что часть надо поменять, но какие именно —
  не сказал. Тексты нижнего баннера писались нами, первый вариант был
  отклонён; нынешний тоже не утверждён. То же с заголовком формы.
- **Город из справочника.** В форме Qbox город выбирается поиском по
  списку. У нас — свободный ввод адреса. Если у Qbox есть справочник
  городов, стоит взять тот же: одинаковые значения избавят от ручной
  чистки данных. Список у заказчика не запрошен.
- **Правый нижний угол подвала пуст.** Там был копирайт (спорный на домене
  КТ), потом телефон — оба отклонены. Что ставить, не решено.
- **Состав тарифов не показывается.** «160+ каналов», «7 онлайн-кинотеатров»,
  различие пакетов 2 SIM и 4 SIM есть в данных, но новый макет карточек их
  не выводит. ТЗ п.4 состав требует.
- **Жёлтый акцент** в нижнем баннере взят из примеров заказчика, но его
  кода нет в гайде — нужен точный оттенок от дизайнеров.
- **Лицензия на Helvetica Neue** для веба. Шрифт коммерческий, риск на
  стороне заказчика.
- **Телефон отдела продаж** — нигде на странице нет. Для холодного трафика
  от блогеров это заметная потеря доверия.

## Как проверять работу

В проекте нет визуальных тестов, поэтому проверка — измерениями в браузере.
Что стоит прогонять после правок оформления:

- горизонтальная прокрутка: `document.documentElement.scrollWidth - clientWidth`
  должно быть `0` на 320, 375, 768, 1024, 1440;
- высота верхнего баннера не больше высоты окна;
- контраст текста не ниже 4.5 (для крупных заголовков — 3.0);
- цели для пальца не меньше 44px;
- обе языковые версии.

`npm test` покрывает только нормализацию телефонов — семь случаев, включая
городские номера Алматы, которые когда-то ошибочно проходили как мобильные.
